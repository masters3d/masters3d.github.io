Engineering work often becomes difficult because too many goals are allowed to
coexist. Improve performance. Refactor the code. Update dependencies. Add tests.
Clean up the dashboard. Each goal may be reasonable, but together they create a
fog where nobody knows what success means right now.

Directed Intentionality is the second sub-pillar of Clear Strategy. It is the
sharp projection of attention toward a specific objective. In the Quest Engine
loop, this is the part of acting that says what the team is doing, what it is
not doing, and how it will know when to stop.

## One vector at a time

The components begin with clear goals. A goal should reduce distraction rather
than add another slogan to the board. "Improve checkout" is not enough. A clear
goal names a target state, a time frame when needed, and the success criteria
that separate done from not done.

The second component is a singular vector of intent. One primary objective gets
privileged. Everything else is secondary or out of scope for the current frame.
This is not because other work has no value. It is because attention fragments
when every worthy thing is treated as equally current.

The third component is minimizing cognitive load. Fewer decisions leave more
energy for execution. Clear constraints, protected focus time, reduced context
switching, and explicit exit criteria let engineers spend less attention asking
"what should I do?" and more attention doing the work.

The final component is action-awareness merger, the flow condition where the
work becomes absorbing because the objective is clear and feedback is immediate.
Directed Intentionality does not create flow alone, but it removes one of the
common blockers: ambiguity.

At early levels, the behavior is understanding the sprint goal, asking
clarifying questions until the assigned task is unambiguous, and avoiding
multitasking. At design levels, it is writing specifications with explicit
success criteria. At system levels, it is shielding the team from competing
demands. At architecture and organizational levels, it is creating focus by
saying no to initiatives that do not serve the chosen direction.

## The failure mode

Without Directed Intentionality, teams thrash. They work hard, but each person
optimizes for a different implicit goal. One engineer refactors for cleanliness,
another chases latency, another broadens test coverage, and another tries to
make the release date. The result is not balanced excellence. It is unresolved
priority conflict.

A common symptom is vague completion. "The feature is done when it works and
looks good" leaves too much judgment until the end. The team discovers late that
people meant different things by works, good, or done.

## How it connects

Directed Intentionality requires Cohesive Narrative because a goal only makes
sense inside a story about the system. It feeds Deliberate Practice because
clear goals make improvement routines targeted. It depends on Challenge Matching
because the chosen objective must fit the team's current capability. Adaptive
Control then steers execution against the goal as feedback arrives.

A concrete example: instead of saying, "Improve checkout performance, refactor,
update dependencies, and improve tests," a team says, "For this sprint, reduce
P95 checkout latency from 800 milliseconds to 200 milliseconds. Everything else
is out of scope." A stronger definition of done can include production latency
below the target for seven days, error rate below the chosen threshold, a
runbook written, and on-call trained. The point is not those exact numbers for
every team. The point is binary clarity.

The practical engineer's caution is that focus can become tunnel vision.
Directed Intentionality should not ignore new evidence. It should make the
current choice explicit enough that Adaptive Control can tell when the plan
needs to change. A clear objective is not a prison. It is a steering target.
