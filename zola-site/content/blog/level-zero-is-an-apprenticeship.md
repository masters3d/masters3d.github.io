Level zero is easy to misunderstand. If a career ladder starts at Level 1, then
Level 0 can sound like a pre-role, a waiting room, or a soft way to say not
ready. I think it is better to name it directly: Level 0 is an apprenticeship.

That word changes the contract. An apprentice is not expected to operate like an
experienced engineer with a smaller title. The expected scope is learning
fundamentals, building baseline productivity, and becoming reliable on
well-defined work. At the same time, an apprenticeship is not passive. The
person learning has real obligations: practice, questions, documentation,
feedback, and steady movement toward independence.

The useful frame is two-sided. The new engineer owns their learning behavior.
The team owns the learning environment.

## What the Apprentice Owns

The Level 0 expectations are concrete: basic programming proficiency in the
team's languages, understanding version control, using the development workflow,
completing small and well-defined tasks, participating in code reviews as a
learner, and documenting learning progress.

Those are not glamorous responsibilities, but they are real. A new engineer can
control the quality of the code they touch. They can control how carefully they
test their own changes. They can control whether they ask clarifying questions
when the specification is unclear. They can control whether feedback from review
changes the next pull request or vanishes after the current one is merged.

That is why learning velocity matters. It is not speed for its own sake. It is
the rate at which feedback becomes changed behavior. A Level 0 engineer does not
need to know everything. They do need to show that new information sticks.

A learning journal, weekly skill goals, before-and-after code examples, and
active questions in review all serve the same purpose. They make growth visible
to the apprentice and to the team. The point is not paperwork. The point is to
turn a confusing first season into evidence that can be reviewed, adjusted, and
trusted.

## What the Team Owns

The team cannot outsource apprenticeship to the apprentice. If every task is
ambiguous, every review is rushed, and every senior engineer is too busy to
explain the why behind the feedback, then the system is asking for independence
without providing a path toward it.

A good apprenticeship needs small tasks that are real enough to matter and
bounded enough to learn from. It needs code review that teaches principles, not
only preferences. It needs room for questions without making the learner feel
like every gap is a defect. It needs documentation that a newcomer can improve
precisely because they can still see where the gaps are.

This connects directly to
[People Systems and the Hiring Pipeline](/blog/people-systems-and-the-hiring-pipeline/).
Hiring for potential only works if the organization has a development system
after the offer. Level 0 is where that promise becomes visible. If the team has
no capacity to mentor, it should be honest about that before treating a beginner
as the problem.

## Reliability Comes Before Scope

The growth indicators at Level 0 are mostly about reliability: meeting delivery
commitments for assigned tasks, asking thoughtful questions, receiving feedback
well, building relationships with immediate team members, and demonstrating a
growth mindset.

That order matters. A Level 0 engineer should not be trying to redesign the
architecture before they understand why the architecture exists. They also
should not wait passively for perfect instructions. The healthy middle is active
learning inside a guided boundary: own the assigned work, ask why, accept
architectural guidance, and build enough context to influence more over time.

The anti-patterns are symmetric. Too external means blaming every bug on unclear
requirements, waiting for perfect tasks, or treating learning as something the
team must pour in. Too internal means taking responsibility for team-level
failures, trying to change systems without enough experience, or interpreting
every review comment as a personal verdict.

An apprenticeship protects against both errors. It says the person is expected
to grow, and the team is expected to teach. It gives the apprentice a control
boundary small enough to act within and visible enough to expand.

That is why Level 0 belongs on the ladder. Not because every company needs a
formal title for it, but because the work exists whether it is named or not. The
first engineering role is not only about writing code. It is about learning how
to become trustworthy in a system of other people, other code, and future
maintenance. That is apprenticeship work, and it deserves to be designed rather
than improvised.
